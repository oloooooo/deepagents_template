# 业务空间名进了 agent 路径，但业务空间**仍然可以改名**

`/memories/{业务空间名}/...` 让 `Workspace.name` 变成了 agent 侧地址的一部分，看起来和
`docs/adr/0002`（公共空间名进路径 ⇒ 名字不可变）直接冲突。**两边的代价不一样，所以结论不一样**：

- 公共空间：改名意味着"另建一个空间"—— 内容挂在那个 id 上，改名要让所有已存在的路径失效，
  而用户文档、别的会话里到处在引用它，所以干脆禁掉改名，要改就删了重建（内容一起没，`docs/adr/0005`）；
- 业务空间：记忆内容按 **id** 存（`(user_id, 空间 id, "filesystem")`），改名只是让**旧会话里
  已经写死的字符串**失效（模型下一轮 `ls` 就看见新名字），内容一份不丢。而项目名是团队日常就会改的
  标签，为此禁止改名不值得。

所以 `WorkspaceService.update(name=...)` 保留，agent 侧则完全不提供改名入口（它连"重命名"这个
动作都没有）：名字只由 REST 改，REST 又按 id 寻址，两边职责清楚。

**Consequences**：改名后旧会话里的 `/memories/{旧名}/...` 会报"不存在"，模型需要重新 `ls`；
`GET /memories/*` 的响应里带的是 agent 能直接用的名字路径（要反查一次名字，`WorkspaceAccess.name_of`）。
把这条和 `docs/adr/0002` 对着读，别把它们"修"成一致 —— 它们是有意不一致的。
