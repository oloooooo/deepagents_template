# 知识库对 agent 恒只读，写入口只有 REST

`/kb/**` 对 agent（模型）一律 `deny` 所有写操作，共享知识与私有文档都一样；
写入口只有 REST，且 v1 只有 super 能写（成员连 REST 写都没有）。

两层理由，缺一不可：

1. **决策层**：用户明确「不能修改空间，公有的不能、私有的也暂时不能」——知识库内容是
   人放进去的资料，模型代笔会让人分不清「这资料是人给的还是模型编的」。注意这与
   `/memories/` 的策略**有意不同**：记忆的 `default` 归 agent 自己维护（写需人工批准），
   知识库没有这个「agent 自己的地盘」。
2. **技术层**：`FilesystemPermission` 在 `create_deep_agent` 时编译期定死，规则里区分不了用户
   （`deny` 会把 super 的 agent 会话一起挡掉）。既然所有人本来就只读，一条静态 `deny` 就是
   完整表达，不需要自定义 backend 做动态判定。

**Consequences**：

- super 想改共享文档只能走 REST，agent 帮不上笔；将来出现「super 要 agent 代笔」的需求，
  再上按 `rt.context` 动态判定的写策略——由需求支撑，不是预防性的；
- 写 deny 规则必须同时列裸路径 `"/kb"`（无尾斜杠匹配不上 `**`，实测能绕过去写到挂载根，
  `/memories/` 踩过这个坑）；挂载 backend 的写方法也要返回错误，作为规则写漏时的第二道防线。
